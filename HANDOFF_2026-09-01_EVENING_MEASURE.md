## 2. Как снять блокировку 1.1 (что известно про машину состояний)

Триггер `sv_guard_journal_daily_claim_mutation` (миграция
`0046_selena_journal_daily_claims.sql`, строки 99–110) разрешает из `EXECUTING` **только**
переходы в `HOLD` и `COMPLETED`. Всё остальное — `JOURNAL_DAILY_CLAIM_TRANSITION_BLOCKED`
(владелица получила эту ошибку живьём, пробуя `NO_SPEND`).

`HOLD` — терминальное состояние (`OLD.status IN ('NO_SPEND','HOLD','COMPLETED')` блокирует любое
изменение) и при этом попадает в список незакрытых. **Перевод в HOLD навсегда замуровывает
проект.** Единственный рабочий выход — `COMPLETED`:

```sql
update sv_journal_daily_claims
set status = 'COMPLETED', completed_at = now(), updated_at = now()
where utc_day = current_date and status = 'EXECUTING'
returning attempt, status;
```

Выполнять в базе сервиса **`Postgres`** (`280e3b59-77c3-46e0-8c2c-75955b7f9a40`), **не** в
`Postgres-selena-v13-restore-20260901` — там этой таблицы нет (она приходит с миграцией 0046, а
восстановленная копия стоит на 43).

После этого повторный прогон в тот же UTC-день требует `SELENA_JOURNAL_FORCE=1` (сравнение
строгое: `process.env.SELENA_JOURNAL_FORCE === "1"`). После 00:00 UTC флаг не нужен.

## 3. Дефекты, которые стоит починить (мы их нашли, но не закрыли)

### 3.1. Нет пути восстановления после убитого прогона — приоритет P0

Любой прогон, который убили (деплой, рестарт платформы, потеря связи с базой), оставляет заявку
в `EXECUTING` навсегда. Снять её можно только ручной операцией в базе, причём единственный
разрешённый выход (`COMPLETED`) записывает неправду: прогон не завершался.

Предложение: аренда с сердцебиением. Обновлять `updated_at` заявки каждые N ответов; при старте
считать заявку брошенной, если сердцебиения не было дольше запаса (например, 45 минут — больше
и очереди pg-boss в 35 минут, и дедлайна Perplexity в 25), закрывать её как `COMPLETED` с
записью в `sv_audit_events` о фактическом расходе и продолжать следующей попыткой без
`SELENA_JOURNAL_FORCE`. Триггер такой переход разрешает — миграция не нужна.

Альтернатива (или дополнение): миграцией добавить легальный переход `EXECUTING → NO_SPEND`
или отдельный статус `ABANDONED`, чтобы бухгалтерия не врала.

### 3.2. Внутренний учёт расходов завышает примерно в девять раз — приоритет P1

За 26 вызовов в `sv_cost_events` записано **$0.26**, а собственная разбивка Bright Data за тот же
день — **$0.0285**:

| Поверхность | Bright Data |
| --- | --- |
| web api ChatGPT Search | $0.0135 |
| web api Gemini Search | $0.0135 |
| web api Google AI Mode Search | $0.0015 |

Причина: когда провайдер не возвращает цену, `resolveBrightDataCost` подставляет
`estimateRunCostUsd("brightdata", …)` = `0.01` за ответ (`packages/lib/src/usage/cost.ts:17`),
намеренно завышенную заглушку. Предварительная смета прогона при этом считается по
`PRICE_PER_ANSWER_USD = 0.0015`, то есть в системе живут три разные цены одного ответа.

Последствие для владелицы: её дневные потолки ($10 в день, $2 на источник) сработают примерно
в девять раз раньше, чем оправдано реальными деньгами.

### 3.3. В биллинге Bright Data нет Perplexity, зато есть Google AI Mode — приоритет P2

Прогон обращается к `brightdata-chatgpt`, `brightdata-gemini`, `brightdata-perplexity`, а в
разбивке провайдера за день значатся ChatGPT, Gemini и **Google AI Mode**. Гипотезы: Perplexity
тарифицируется позже (у него асинхронный режим `trigger`), либо датасет
`gd_m7dhdot1vw9a7gc1n` на этом аккаунте отдаёт не то, что мы думаем. Нужна сверка.

### 3.4. Потолок миграций 51 не даст применить 0052 и 0053 — приоритет P1, ловушка

`SELENA_MIGRATION_MAX_INDEX=51` у сервиса `migrate` (и в генераторе compose,
`apps/cli/src/index.ts`). В ветке сейчас 54 миграции (0000–0053).

Сегодняшний staging это переживает: он получил вариант `0045` из ветки PR #96, где колонка
`legacy_collision_ordinal` уже была. **Но любая свежая база**, промигрированная с потолком 51,
получит канонический `0045` без этой колонки, не получит `0053` — и `measure` снова упадёт на
`there is no unique or exclusion constraint matching the ON CONFLICT specification`.

Поднять потолок до 53 нужно осознанно и до появления любого нового окружения.

### 3.5. Строгое сравнение флагов ломается о невидимый пробел — приоритет P2

`SELENA_JOURNAL_FORCE === "1"` и `SELENA_MEASUREMENT_ENABLED`/`SELENA_EMERGENCY_STOP` того же
рода. Владелица потратила час, потому что значение выглядело как `1`, а сравнение не совпадало.
Достаточно `.trim()` и признания `1|true|yes`.

### 3.6. Пропускная способность на нескольких клиентов не проверена — приоритет P1 до продаж

Очередь `selena-measure` в `apps/worker/src/index.ts` создаётся без настройки параллелизма, а
`measure-journal.ts` держит собственный потолок в 6 одновременных ответов. Что произойдёт при
десяти клиентах сразу — неизвестно; при нынешней скорости последовательная обработка растянется
на сутки. Нужна проверка лимитов Bright Data по аккаунту и решение по параллелизму между
проектами, а не только внутри одного.

### 4.2. PR #103 — рассогласование кода и базы, из-за которого падал каждый замер

Симптом: `there is no unique or exclusion constraint matching the ON CONFLICT specification`.
База несёт индекс `(project_id, version, legacy_collision_ordinal)`, а код на ветке называл

Исправление перенесено из `ec4d8b2b` (черновой PR #96, 139 файлов, к слиянию не предназначен).
Codex справедливо возразил на первую версию: править уже применённую `0045` бессмысленно —
журнал её не переиграет. Поэтому `0045` вернулась к исходному виду, а колонка, обратная

`0053_configuration_lock_legacy_collision_ordinal.sql`, идемпотентную для обеих форм базы.

Отрепетировано на одноразовом PostgreSQL 16: старая форма обновляется, staging-форма проходит
без изменений, повторный прогон ничего не меняет, порядковые номера старых дублей сохраняются.

### 4.3. Найдена настоящая причина, почему measure «не видел» новый код

**У сервиса `measure` вообще отсутствовала связь с GitHub** (`build: {}`, автодеплой
`reason: NO_REPO`). Все «деплои» были переиспользованием образа от PR #101, поэтому ни одна
правка до него не доезжала. Связь восстановлена: репозиторий, ветка
`release/selena-visibility-mvp`, `rootDirectory: "."`, `dockerfilePath: docker/Dockerfile`.

Затем выяснилось обратное: с автодеплоем мерж любого PR обрывает идущий замер (так и случилось
с #104 — прогон убит на 26/75). Автодеплой по пушу отключён через
`watchPatterns: ["docker/never-matches-so-pushes-do-not-restart-a-paid-measurement"]`; связь с
репозиторием сохранена, ручная сборка по-прежнему берёт свежий код.

### 4.4. PR #105 — ускорение впятеро

Две независимые причины медленности:

1. `inPool` был не пулом, а циклом по пачкам: ждал все три ответа, прежде чем начать следующие
   три. Один вызов Perplexity (15 минут) держал два соседних слота пустыми.

Пул переписан на скользящий (слот освобождается сам по себе), потолок поднят до 6, окно
снимка для ChatGPT и Gemini расширено с 10 до 15 минут. Шесть, а не десять, сознательно:
прогон 29 августа потерял 200 ответов из 200 (`MALFORMED_RESPONSE`) именно из-за
параллелизма против пятиминутного окна.

Измерено на живом прогоне: **12 ответов за 12 минут** против 49 минут до правки.
