## Baseline routes whose built behaviour differs (spot findings, not a full diff)

- **`/api/local-ready/`**: the baseline file always returns `{status:"ok"}` with 200. The build does not ship it and replaces it with #1, which returns 503 until the schema and report routes are ready.
- **`/api/v1/selena/payments/test`** (baseline source exists): the underlying `selena-test-payment-store` in the build (`selena-test-payment-store-CFV9wYz0.mjs`) adds `requireLocalOrder`, `localSnapshotSha256` and an `authorize` callback. The baseline store has none of these.
- `local-scan-cycles/$cycleId/report` responses now include the `documents` field from the hard-coded report library.

## Security findings

1. **Client data and hard-coded IDs in code.** `selena-report-library-DaJj8lm0.mjs` hard-codes a tenant UUID, a project UUID and a cycle UUID. The two client report HTML files are bundled as JS chunks: `avli-15-queries-VppL96i4.mjs` (142,806 B) and `avli-first-measurement-BamEN-AV.mjs` (12,665 B). Route #2 has **no env gate**, so the data ships with any build. Do not port. Move the documents to tenant-scoped storage.
2. **Staging gate is an environment ID.** #3-13 are gated on the literal Railway staging environment UUID plus a flag. Porting them needs explicit feature flags that are hard-off in production, not an environment-ID check.
3. **RLS depends on the connection role.** The web `db` uses `DATABASE_URL` (the legacy connection) unless `SELENA_RUNTIME_DATABASE_CA_PEM` is set. `sv_local_order_publications`, `sv_local_customer_runs/_tasks` and the Local Maps report tables have RLS **enabled but not FORCED**; only 24 tables, including `sv_local_ai_*`, are FORCE. If the connection role owns these tables, RLS is bypassed and isolation rests only on the explicit `organization_id = tenant` predicates. Every query I inspected had those predicates, so **no IDOR was found**, but there is no defense in depth. Verify which role is used; apply FORCE RLS or use a non-owner runtime role.
4. **"Admin" means a tenant owner or admin.** Routes #14-19 check only `requireLocalOperator` (tenant `owner`/`admin`). A customer owner can canary-review, QC, publish and deliver their own report. Platform QC integrity is not enforced. Add a platform-operator check if QC is meant to be Selena staff.
5. **The self-pay path unlocks publication.** #9 lets any tenant owner record a SUCCEEDED $49 `test` payment. `sv_publish_local_order` (0076:48) accepts exactly that as the precondition for publishing. Never enable this outside staging, and do not port it.
6. **Uneven CSRF protection.** #14-21 accept requests with **no** `Origin` header. They rely on the required `Idempotency-Key` custom header, which forces a CORS preflight. #3, #4-10 and #12-13 require an exact Origin match. Make the report routes consistent.
7. **Ambiguous tenant selection.** `resolveSessionAuthContext` falls back to `rows[0]` without `ORDER BY` when there is no `activeOrganizationId`. A user in several orgs can resolve to an arbitrary tenant. This is a wrong-tenant risk, not a cross-tenant leak.
8. **Unauthenticated self-fetch.** #1 is anonymous and runs a DB catalog query plus two loopback HTTP calls on every hit, with no cache or rate limit. That makes it a minor denial-of-service amplifier.
9. **Schema provenance gap.** The `sv_local_ai_*` tables used by #3 exist only in the staging schema, from the unrecovered migration 0077. Porting #3 means reconstructing that migration first.
10. **Response codes.** Cross-tenant mutations on #14-18 return **400** `LOCAL_CYCLE_NOT_FOUND` instead of 404. There is no leak, but tests should pin a 404 contract.
