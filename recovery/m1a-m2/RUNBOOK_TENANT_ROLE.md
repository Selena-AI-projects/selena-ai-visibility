# Включение изоляции клиентов на staging (роль `selena_app`)

Весь код для изоляции уже в `release/selena-visibility-mvp`. Этот документ описывает, как владелец окружения включает её на Railway. Все шаги выполняет владелец. Агент окружения не трогает.

Порядок: сначала **staging**, потом production и только после проверки staging. Воркер (`worker`) в этом этапе не меняется, он остаётся на подключении владельца.

## Состояние staging (проверено 2026-09-25)

Staging устроен не так, как предполагает эта инструкция:

- Шаг 1 выполнен: журнал 82/1790320003000.
- `web` и `worker` уже подключаются к базе как `selena_app` через свой `DATABASE_URL`, `migrate` и `measure` — как владелец.
- Роль `selena_app` уже существует. Миграции 0068–0071 выдали ей права на новые функции (проверено `has_function_privilege`).
- **Шаг 2 на staging не выполнять.**
  - Скрипт сменит пароль роли, под которой сейчас работают `web` и `worker`.
  - Скрипт начинается с `REVOKE ALL ON ALL TABLES IN SCHEMA public`. Он заберёт права на staging-only таблицы `sv_local_*`, которых нет в его списке.
- `SELENA_WEB_DATABASE_URL` у `web` указывает на старую базу Supabase, а не на Railway. Шаг 3 возможен только после замены этого значения на `${{DATABASE_URL}}`.

## 0. До начала

- Сделать резервную копию базы staging в Railway (Postgres → Backups).
- Пароль для новой роли сгенерировать у себя, например `openssl rand -hex 24`. Hex-пароль не нужно экранировать в URL. Пароль не пересылать в чат и не сохранять в Git.

## 1. Миграции 0068–0071 (сервис migrate)

1. В переменных сервиса migrate поставить `SELENA_MIGRATION_MAX_INDEX=71`, затем Deploy.
2. Первый запуск остановится с `SELENA_MIGRATION_OWNER_APPROVAL_REQUIRED` и напечатает строку вида `Set SELENA_MIGRATION_APPROVED_SHA=<sha>`. Так и должно быть: без явного одобрения миграции не применяются.
3. Поставить `SELENA_MIGRATION_APPROVED_SHA=<sha из лога>` и сделать Redeploy.
4. В логе должно быть `journal after: 82/1790320003000` и `migrations complete`.

Что должно получиться:

- 78 записей было, 4 добавилось.
- Пять собственных Local-миграций staging, записанных после 0067, программа признаёт историческими и пропускает. Миграции 0068–0071 ложатся поверх них без конфликтов имён.
- Если журнал базы не совпадает с ожидаемым, программа остановится с `SELENA_MIGRATION_JOURNAL_MISMATCH` и ничего не применит.

Эти миграции добавляют политики RLS и функции `SECURITY DEFINER`. FORCE не включён, поэтому на подключения владельца они не влияют. Сервисы, которые уже работают как `selena_app`, с этого момента видят строки только в рамках `app.organization_id` / `app.user_id`.

## 2. Роль `selena_app`

Скрипт выполняется подключением **владельца**, строка `DATABASE_URL` сервиса Postgres:

```sh
psql "$OWNER_DATABASE_URL" -v role_password='<пароль из шага 0>' \
  -f packages/lib/scripts/selena-rls-runtime-role.sql
```

- Скрипт сам проверяет, что миграции до 0071 применены. Если нет, он остановится с `SELENA_RUNTIME_ROLE_REQUIRES_MIGRATION_0071`.
- Повторный запуск приводит права роли к списку из скрипта и отзывает всё, чего в нём нет. На базе с таблицами вне этого списка (staging) скрипт не запускать.

## 3. Переключение web

В переменных сервиса **web** добавить переменные в указанном порядке. `SELENA_DATABASE_SURFACE` ставится последней.

| Переменная | Значение |
|---|---|
| `SELENA_WEB_DATABASE_URL` | Тот же адрес, что в `DATABASE_URL`, но пользователь `selena_app` и пароль из шага 0 |
| `SELENA_INTERNAL_DATABASE_URL` | Текущий `DATABASE_URL` владельца. Нужен для админских страниц и хранилища секретов |
| `SELENA_PGBOSS_OWNER_MANAGED_SCHEMA` | `true` |
| `SELENA_HOSTED` | `true`. Если какой-то URL не задан, web не запустится, а не тихо вернётся к владельцу |
| `SELENA_DATABASE_SURFACE` | `web` |

Затем Deploy.

## 4. Проверка

1. Web запустился, в логах нет `_REQUIRED`.
2. Подключением владельца выполнить:
   ```sql
   select usename, count(*) from pg_stat_activity
   where datname = current_database() group by usename;
   ```
   В результате должна быть строка `selena_app`.
3. В кабинете:
   - войти;
   - открыть свой бренд, промпты и отчёт;
   - открыть админскую страницу;
   - создать тестовую организацию или бренд.

   Всё должно работать как раньше.

## 5. Откат

Удалить у web переменную `SELENA_DATABASE_SURFACE`. `SELENA_HOSTED` удалить тоже, затем Redeploy.

- Web вернётся на подключение владельца.
- Миграции 0068–0071 и роль можно оставить: без FORCE они на владельца не действуют.

## Production

Шаги те же. Перед шагом 1 нужно убедиться, что журнал production совпадает с Git. Если не совпадает, программа миграций остановится с понятной ошибкой и ничего не применит, и тогда нужно сначала разобраться с расхождением.

## Дальше, не в этом этапе

- FORCE ROW LEVEL SECURITY.
- Отдельная роль `selena_worker` для воркера.
