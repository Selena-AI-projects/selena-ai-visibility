# M5: еженедельный отчёт клиенту в Telegram

## Что уже есть

Staging-репетиция всей цепочки, закреплённая за тестовыми данными (миграции 0063 и 0064):

- `packages/lib/src/selena-telegram-adapter.ts` — `sendTelegramMessage`, `parseTelegramStartUpdate`, `setTelegramWebhook`. Токен редактируется, таймаут 15 с.
- `packages/selena-visibility-contracts/src/staging-simulation.ts`:
  - подписанная одноразовая ссылка `t.me/<bot>?start=<token>` со сроком 15 минут;
  - политика доставки: 5 попыток, паузы 1 мин / 5 мин / 30 мин / 2 ч, аренда 30 с;
  - классификация ответа Telegram.
- Таблицы `sv_simulation_{recipients, reports, deliveries, delivery_attempts}`. CHECK-ограничения запрещают в них всё, кроме `staging`, `test` и `sample`.
- Webhook и шаги оркестрации — только под `/staging/`.

Чего нет:

- боевых таблиц;
- еженедельной задачи в воркере (`recurring-schedules.ts` знает только три очереди);
- кнопки подключения в кабинете;
- настоящего дайджеста: `buildDigestMessage` требует маркер `[TEST]`.

## Решения по умолчанию

Владелец может изменить любое из них. Пока он этого не сделал, работа идёт так:

| Вопрос | По умолчанию | Почему |
|---|---|---|
| HOLD из Architecture v1.4 §11 | Код пишется, но всё выключено флагом `SELENA_WEEKLY_DIGEST_ENABLED`. Реальные сообщения — только после явного разрешения владельца. | Раньше на HOLD стоял выпуск функции, а не разработка. |
| Кто получает | Организации с тарифом, в котором есть еженедельный замер ($49 Snapshot, $79 Landscape), и пилоты, которым оператор включил доставку вручную | `OFFER_LADDER.md:12-13` |
| Когда отправлять | Раз в неделю, в понедельник около 06:00 UTC, **только если за неделю завершился новый цикл замера**. Нет нового цикла — нет сообщения. | Сообщение не должно выдумывать изменения. |
| Что в сообщении | Число систем, в которых бренд упомянут; изменения относительно прошлого цикла из `computeCycleDiff` (появился, исчез, сдвинулся); ссылка в кабинет. Никаких сводных оценок. Нет данных — пишем «неизвестно», а не ноль. | Правила отчёта `REPORT_DESIGN_SPEC.md` |
| Язык | Русский. Английский — если язык отчёта организации английский. | Аудитория |
| Бот | Один бот Selena. Токен задаёт владелец в Railway. Я бота не создаю и webhook в production не регистрирую. | Внешнее действие |
| Chat ID | Хранится зашифрованным, как в 0063. Одна привязка на организацию, проект и канал. | Уже проверено на staging |

## Шаги (PR)

1. **Миграция: боевые таблицы доставки.**
   - `sv_delivery_recipients`, `sv_weekly_digests` (снимок содержимого до отправки), `sv_digest_deliveries`, `sv_digest_delivery_attempts`.
   - Схема как у simulation, но без тестовых маркеров. RLS по организации с FORCE.
   - Одна неделя — один дайджест на проект.
2. **Контракты и сборка дайджеста.**
   - Вынести из `staging-simulation.ts` общие части: токен, ссылку, политику доставки.
   - Написать `buildWeeklyDigest(report, diff)` и текст на RU и EN.
   - Тесты: нет нового цикла — нет дайджеста; неизвестное не превращается в ноль.
3. **Подключение Telegram в кабинете.**
   - Кнопка «Подключить Telegram» выдаёт одноразовую ссылку.
   - Боевой webhook-маршрут проверяет секретный заголовок и не зависит от staging.
   - Есть кнопка «Отключить».
4. **Еженедельная задача в воркере.**
   - `selena-weekly-digest` в `MANAGED_SCHEDULES`.
   - Задача сохраняет дайджест, затем доставляет его с политикой повторов.
   - Выключена флагом. Tenant scope на каждую организацию.
5. **Проверка на staging.** Тестовый бот, одна организация, одно сообщение. Только после разрешения владельца.

Не делаем: email-дайджест (отдельное решение), настройки частоты, групповые чаты.
